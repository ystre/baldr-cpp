= Baldr User Guide

== Running the built target

`baldr run` automatically discovers the built executables. Baldr looks for an
executable with the same name as the target.

The discovery mechanism is slightly different depending on the project type.

* CMake projects: recursively looks in the tree under `build/<build_type>`.
* Make projects: looks directly in `build`. No support for build types.

== Listing targets

`baldr targets` prints the buildable targets of a CMake project, one
`<name><TAB><type>` line each, sorted by name:

----
$ baldr targets
baldr	executable
builder	static_library
----

The types are CMake's, in lower case. Interface libraries and the CTest
dashboard targets (`Nightly*`, `Continuous*`, `Experimental*`) are left out. A
Makefile project lists nothing.

The listing comes from the CMake File API: Baldr asks for the code model in
every build directory it configures. `targets` configures the project first if
`build` would.

The log goes to standard error only, and no log file is written.

== Shell completion

Baldr completes its commands and options in bash and zsh, and the targets of
`-t/--target` through `baldr targets`: every target for `build`, executables
only for `run`. The `-p`, `-b` and `--build-dir` already on the command line
choose the project. Completing a target of a project not configured yet runs
the configure step, which can take a while.

The scripts ship in `share/baldr/completion`. The installer offers to install
them, or takes `--completion` or `--no-completion` after `--`:

----
./baldr-installer -- --completion
----

It copies them to the standard directories under the installation prefix:

* bash: `share/bash-completion/completions/baldr`, loaded by bash-completion on
  first use. Without bash-completion, source the file from `~/.bashrc`.
* zsh: `share/zsh/site-functions/_baldr`. The directory has to be on `$fpath`
  before `compinit` runs; the installer prints the line for `.zshrc` if it
  finds no mention of it there.

== Compile commands

CMake projects are always configured with
`-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`, and a symlink is created in the root of
the project for LSP servers.

== Configuration file

The global (in HOME) and project-local configuration files are merged. They are
called `.baldr.<ext>` and the extension can be YAML, JSON or TOML. the two need
not be in the same format, and more than one in the same directory is an error.

The merging behaviour:

* maps (`env`, `cmake.definitions`) merge key by key
* anything else (a list such as `debugger-args` too) replaces the global value
* empty or null value deletes the key, for example,  `build-type:` resets it to
  Baldr's default and an empty entry under `env` or `cmake.definitions` drops
  the one inherited from the global file. Applicable to YAML and JSON only.

CLI flags always take precedence over both files.

A missing or empty file (or one with only comments) is the same as no
settings; anything else must be a map.

[source,yaml]
----
debugger: gdb
debugger-args: [--args]
build-type: Debug
env:
  CMAKE_BUILD_PARALLEL_LEVEL: 8
cmake:
  definitions:
    CMAKE_CXX_STANDARD: 23
docker:
  mount-baldr: true
  baldr-path: /path/to/baldr
----

The values under `env` and `cmake.definitions` take any scalar as its text, but
a number keeps only its numeric value, so quote a version such as `"1.10"`.

== Logging

Baldr's output is shaped by a few independent settings, each an environment
variable.

[cols="2,3,2"]
|===
| Variable | Values | Default

| `SPDLOG_LEVEL`
| `trace`, `debug`, `info`, `warn`, `err`, `critical`, `off`; per logger as
  `<logger>=<level>`, comma-separated (e.g. `debug,docker=off`)
| `info`

| `BALDR_LOG_FORMAT`
| `plain` (message only), `timestamped`, `epoch` (`1761656592.123456 W message`)
| `plain`

| `BALDR_LOG_VIEW`
| `stream` (every line), `window` (rolling window, replayed on failure),
  `digest` (errors and warnings as one-liners, then a summary)
| `stream`

| `BALDR_LOG_FILE`
| Directory of the log files, empty for none
| `/tmp/baldr-logs`

| `BALDR_LOG_FILE_FORMAT`
| As `BALDR_LOG_FORMAT`
| `epoch`

| `BALDR_LOG_WINDOW_SIZE`
| Lines shown by `window`
| 10

| `BALDR_LOG_LINE_WIDTH`
| Length cap of a `digest` line
| 160

| `BALDR_LOG_DIGEST_LINES`
| Lines shown by `digest`, for each of errors and warnings; the summary counts
  the rest as `not shown`
| 20
|===

Each run writes the full record to
`<dir>/<YYYYMMDDTHHMMSS.mmm>Z_<project>_<command>.log`, at least at `info`
level and without ANSI colors, whatever the terminal shows. The digest ends
with its path:

----
src/noisy.hpp:2:26: warning: unused variable ‘unused’ [-Wunused-variable]
src/b.cpp:2:28: error: ‘undeclared_thing’ was not declared in this scope
make[2]: *** [src/CMakeFiles/hello.dir/build.make:107: src/CMakeFiles/hello.dir/b.cpp.o] Error 1
Build failed (exit code 2). 2 errors, 1 warning, 2 repeated, full log: /tmp/baldr-logs/20261028T153609.675Z_proj_build.log
----

Lines of the build tools get their level from their content, see
<<classifier>>.

A nested `baldr` streams plain lines for the outer one to re-log and writes
no log file of its own. This is what `-i/--image` relies on, as the container
runs Baldr again; it applies the same way to a `baldr` called from a build
step.

=== Classifying output

Baldr has the capability of classifying the log levels coming from its
subprocess. Primary use-case is for `digest` logging mode avoiding littering
the output.

The rules that give each line of subprocess output its level come from
`share/baldr/classifier.toml`, installed next to the `bin` directory of Baldr. It
can be replaced by a `classifier.<ext>` in any of the configuration formats, and
more than one in the directory is an error.

It has one named set of rules per tool: `make`, `ninja`, `gtest`, `ctest`,
`sanitizers`, `linker`, `gcc` (for Clang too) and `cmake`. Baldr itself knows
none of these tools.

The names let a project change one tool without touching the others: leaving a
set out of `use` turns that tool's rules off, and a set of the same name
replaces them.

* `use` lists the sets in effect, in matching order.
* A rule has a `level` (`trace`, `debug`, `info`, `warning`, `error`, `critical`)
  and the markers it `contains`, plain substrings of the line.
* The first matching rule decides, and a line nothing matches is `info`. ANSI
  escapes in the line during classification are ignored.

A `classifier` section in the configuration file goes on top of the shipped file
with the same merging behaviour: `use` replaces the shipped list, and a set
replaces the shipped set of that name or adds a new one. A set takes effect only
if `use` names it, so to extend the shipped sets, repeat them there:

[source,toml]
----
[classifier]
use = ["mytool", "make", "ninja", "gtest", "ctest", "sanitizers", "linker", "gcc", "cmake"]

[[classifier.sets.mytool]]
level = "error"
contains = ["MYTOOL FAILED"]
----

Without the shipped file, as with a `baldr` binary copied alone, Baldr warns and
logs every line as `info`, unless the configuration file has rules of its own.
In `digest` view that leaves only the warning and the summary, with the output
in the log file.

== Using a container

`-i/--image <image>` on `build` or `run` re-executes the equivalent Baldr
invocation inside a fresh container of `<image>` instead of running it on
the host:

* The resolved project directory is mounted to `/workspace` inside the
  container, and the container-side invocation uses `--project /workspace`.
* Baldr's own binary is mounted in (read-only, to `/usr/local/bin/baldr`) and
  used as the container-side `baldr`, so the image doesn't need to bundle its
  own copy. Set `docker.mount-baldr: false` in `.baldr.yaml` if the image
  already provides one; `docker.baldr-path` overrides the host path that gets
  mounted (default: the running `baldr` binary itself, via `/proc/self/exe`).
  The `share/baldr` directory beside that binary is mounted along with it, to
  `/usr/local/share/baldr`.
* The container process runs as the host's `uid:gid`, so files written into
  the mounted project directory (build output, generated files) end up
  owned by the same user as on the host.

The target image must already have the project's toolchain (compilers,
CMake, etc.) installed — `--image` does not provision one.

== Interrupting Baldr

Ctrl-C stops what Baldr is running instead of abandoning it mid-build:

* The first Ctrl-C asks the build or `run` target to stop; Baldr waits for it.
* The third force-kills it, for a child that ignores Ctrl-C, such as a program
  under `--debug` or when a child is slow.

During a build, each press is logged:

----
Interrupt received: stopping `make`, 2 more interrupt(s) to force-kill.
make: *** [Makefile:2: all] Interrupt
Interrupted.
----

An interrupted build is not reported as failed, and Baldr exits with status
130, like any command stopped with Ctrl-C.
